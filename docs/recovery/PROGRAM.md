**Architecture contracts**

1. **Configured source identity.** `providerTypeID` identifies implementation type; persisted `providerInstanceId` identifies one configured source. IDs survive reorder, labels, reload, and restart. The configuration add/migration boundary assigns them once. Provider default factories remain ID-free and return fresh nested structures. Runtime reconstruction does not invent identity.
2. **Settings ownership.** A plugin-owned store normalizes versioned data, preserves unknown fields/providers, exposes immediate canonical updates by ID, and serializes persistence. UI receives independent drafts; conflicting stale drafts require visible recovery instead of silently replacing newer data. Deleted IDs cannot be resurrected by stale callbacks. Preserve a recoverable, Git-ignored original-data copy before the first schema-changing write. Malformed/future data disables every persistence path, including UI edits, retry, flush, and unload, until safe recovery is established. The storage boundary must expose actual read, parse, and write failures: inspected Obsidian versions swallow errors inside `loadData`/`saveData`. Ordinary disable/re-enable must hand off pending persistence between plugin instances before the successor reads settings. Flush/retry behavior is explicit; no promise that Obsidian awaits asynchronous unload or protects against process termination.
3. **Suggestion meaning.** Retain familiar labels, but distinguish real file targets, deliberate unresolved links, literal text, and actions. Real targets preserve the file and optional alias; native link generation uses the source note and user preferences. Deduplication uses target/alias or action identity. Identical labels may remain visible with useful path/source context.
4. **Action outcomes.** An editor-independent creation operation returns the actual file, cancellation, or failure, with explicit collision behavior. It owns neither modal prompts nor editor transactions nor CLI discovery/IDs. The insertion coordinator catches synchronous/async errors, prevents duplicate execution, and validates editor, source-document revision, range, expected content, and lifecycle before applying a delayed result. Unload, document replacement, source deletion, or editor reuse invalidates pending insertion. A created file remains discoverable even if later insertion is cancelled. Intentional unresolved-date fallback must not masquerade as successful creation.
5. **Cache/lifecycle.** Cache by configured provider and trigger, with explicit query dependence and bounded entries. Invalidate on configuration/data/lifecycle changes and retain a limited freshness fallback where integration indexes lack reliable events. Catch failures during construction, ordinary suggestions, and creation suggestions independently. Optional integrations can become available after startup.
6. **Integration boundaries.** Providers do not perform network/shell work during lookup. Parsing and naming are separate from note creation. Templater's active-editor insertion API needs a dedicated investigation: capturing coordinates or checking a substring is not enough if the integration itself mutates the editor after awaiting. Resolve this before claiming complete action safety.

**How delegated work is controlled**

- Every significant task gets the product intent, verified base, allowed files, contract, exclusions, acceptance cases, predecessor PRs, and a request to return a PR URL and exact head SHA. It owns an isolated worktree and never merges itself.
- Keep at most two substantial implementation lanes active while the core contracts change: one runtime lane and one independent tooling/validation lane. Use short-lived sub-agents for narrow repros, adapter research, and focused fixes.
- The owner retains architecture, compatibility, feature ordering, UX decisions, and release acceptance. Delegate implementation, not these decisions. If a task needs broader scope, update the brief before it expands.
- PR readiness triggers a fresh reviewer who did not author the changes. Settings migration and async editor changes receive both a code/state-transition review and a runtime/UX review where applicable. Reviews identify exact head SHA, actionable findings, reproductions, and test gaps.
- Route findings back to the implementation task. After fixes, review the changed head and rerun relevant checks. Do not accept stale review results, green tests that mock away the failing boundary, or a worker's self-review as final approval.
- The owner checks the complete diff, accepted scope, current CI, unresolved discussions, and regression evidence before merging the reviewed revision. Integrate one core PR at a time; verify the resulting master before dispatching its dependent packet.
- At each handoff the coordinator updates STATUS.md with task ID, branch/worktree, PR/head, validation evidence location, reviewer/findings, exact reviewed revision and resulting master SHA, accepted decisions, blockers, and next owner/action. Keep one maintained program rather than accumulating contradictory plans. Completion reports must be sent back to the coordinator task so idle coordination resumes.

**Release gate and stop conditions**

Use a dedicated fixture vault with installation under `.obsidian/plugins/entities`. Do not use the personal development vault as the only test environment. Fixtures contain two same-type providers, duplicate filenames/aliases, representative templates, dates, malformed/absent properties, and optional-dependency states.

Required evidence: old-settings upgrade; clean install; correct links under preferences; creation failure/cancellation/collision/rename; editing/switching notes during actions; main/popout editors; source/Live Preview; mobile keyboard/touch/IME; repeated load/settings/unload; minimum/current runtime and compatible integration versions. Record exact available devices/runtime/integration versions and the responsible tester; unavailable hardware is an explicit acceptance gap. Measure cold start and suggestion latency on a representative large vault before adding lazy dictionaries or optimizing caches; no arbitrary performance claims.

Repair release scripts so version/tag/assets agree, failed prerequisite checks stop publishing, and dry runs have documented side effects. Update architecture/provider authoring guidance alongside changed contracts. Before deploying a migrated build into a real vault, preserve the original `data.json` and previous artifact; test restoring both after fully quitting Obsidian and confirming its process has exited. Disabling the plugin alone leaves an in-memory dirty predecessor able to overwrite a manual restore on re-enable. A Git revert cannot undo a settings migration. Record tested artifact checksums, versions, and concrete dogfood sessions; promote those same assets rather than rebuilding untested master. Explain the minimum-version change and downgrade procedure. Use applicable Obsidian preview/release scans if community distribution is pursued. [Developer review process](https://obsidian.md/blog/future-of-plugins/).

Do not label recovery complete while any known settings-loss, wrong-target, stale-editor-write, or misleading-creation-success defect remains.
